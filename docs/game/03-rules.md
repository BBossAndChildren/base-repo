# 게임 규칙 · 상태 필드

> 2026-10-31 작성한 **1차 구현·밸런스 초안**이다. 아래 숫자는 테스트를 위한 시작값이며 사용자 평가·실측으로 검증된 값이 아니다. 실제 구현 상태와 구분한다. 게임 흐름은 [시나리오](02-game-scenario.md), API 계약은 [개발 명세](../development/03-api.md)를 참고한다.

## 1. 공통 원칙

- 플레이어는 현재 나이와 상황에서 시작한다. 행동과 사건에 따라 게임 시간이 흐르고, 인생은 캐릭터의 죽음을 기점으로 끝난다. 죽음의 발생 조건·방식은 미정이다.
- AI는 대사와 상태 변경을 **제안**한다. 백엔드는 실제 발생한 행동·현재 상태·허용 범위를 검증해 확정하고, 프론트에는 확정된 값만 반환한다. 사용자의 주장이나 NPC의 추측만으로 직업·역량·경험이 자동 확정되지 않는다.
- 아래 에너지는 **가상 캐릭터의 게임 수치**다. 실제 사용자의 건강·질병 정보를 묻거나 입력하도록 유도하지 않고 플레이어 기록에 저장하지 않는다.
- 수치는 현실의 소득·능력·심리 상태를 진단하거나 직업 적성을 확정하는 점수가 아니다. 관심과 역량은 서로 따로 관리한다.

## 2. 필드 · 형태 · 초기값 · 화면 표시

아래 키와 수치는 AI·백엔드·프론트가 확인할 **공유 제안안**이다. 기존 API의 `state` 상세 형식이 확정되었다는 뜻은 아니다. 상태 패널은 나이부터 우선 구현하고 다른 항목은 연동 합의 전까지 숨긴다.

| 키 | 의미와 형식 | 시작값 | 범위 | 화면 표시 1차안 |
|---|---|---|---|---|
| `age` | 게임 속 현재 나이, 정수 | 사용자가 입력한 현재 나이 | 0 이상. 최대 나이와 입력 허용 범위는 미정 | 표시 |
| `elapsedDays` | 플레이 시작 이후 흐른 게임 날짜, 정수 | `0` | 0 이상, 상한 없음 | 숨김. 필요할 때 사건 경과로 표현 |
| `funds` | 생활·준비·사업 등에 쓸 수 있는 **추상 자금 지수**, 정수 | `50` | 0~100 | 연동 후 표시 제안 |
| `energy` | 가상 인물의 활동 에너지, 정수 | `70` | 0~100 | 연동 후 표시 제안 |
| `ability` | 활동 경험으로 형성되는 **게임 내 전반적 역량 지수**, 정수 | `20` | 0~100 | 연동 후 표시 제안. 실제 능력 판정이 아님 |
| `relationship` | 만난 NPC별 관계 지수 객체: NPC 식별자 → 정수 | `{}`. NPC와 관계가 생기면 해당 인물 `50` | 각 인물 0~100 | 개별 값 표시 여부 미정, 우선 숨김 |
| `interests` | 분야별 관심 지수 객체: 분야 → 정수 | `{}`. 사용자가 시작 입력에서 선택했거나 직접 관심을 표현한 분야만 `50`으로 추가 | 각 분야 0~100. **없는 분야는 미확인**이며 0이 아님 | 우선 숨김. 추천 근거로 활용 가능 |

`funds`, `energy`, `ability`는 모든 플레이어에게 같은 임시 시작값을 적용한다. 나이·현재 상황을 점수로 추정하지 않는다. 입력한 기존 관심사와 희망 직업은 프로필에 저장하며 관심 표현과 희망 직업 확정은 구분한다. 시작 때부터 알고 있는 NPC·관계 생성 방식은 별도 결정한다.

## 3. 시간 · 나이의 진행

- `elapsedDays`는 게임 시작 시점부터 지난 **게임 속 날짜**다. 행동에 따라 증가하며 소모 후 회복하는 점수가 아니다. 과거 날짜로 되돌리지 않는다.
- 기준 초기 나이를 따로 보관하고 `age = 시작 나이 + floor(elapsedDays / 365)`로 계산한다. 실제 생일이 없는 게임용 근사치이며 시작 나이를 매번 더하지 않는다.
- 1차 시간 예시: 일상 대화·짧은 행동은 `+0일`, 하루를 보내는 활동은 `+1일`, 기간을 정한 교육·근무는 **실제로 진행된 게임 날짜만큼** 더한다. 날짜 단위 미만의 활동도 사건과 순서는 남긴다.
- 3D 전환 자체나 화면 로딩·재시도만으로 날짜를 더하지 않는다. 실제 행동의 시간은 같은 사건에서 중복 적용하지 않는다.
- 어린 시기와 일상 구간을 빠르게 압축하고 직업 체험을 충분히 보여주는 것이 방향이다. 나이별 구체적 진행량·최대 플레이 기간·죽음 조건은 미정이며, 약 15분은 강제 종료 시간이 아닌 권장 시간이다.

## 4. 변화 규칙 1차안

다음 값은 **실제로 해당 행동·결과가 확정된 경우**의 검증용 기본 변화량이다. 단순 발언, 제안, 3D 장면 진입만으로 적용하지 않는다. 한 사건에서 같은 효과를 중복 적용하지 않는다.

| 확정된 사건 | 변화 1차안 | 설명 |
|---|---|---|
| 하루 활동 | `elapsedDays +1`, `energy -5` | 하루를 보낸 것으로 확정된 경우 |
| 하루 휴식 | `elapsedDays +1`, `energy +10` | 휴식이 실제로 진행된 경우. 별도 하루 활동 효과를 중복하지 않음 |
| 학습·연습 완료 | `energy -5`, `ability +2` | 학습 행동의 결과가 확정된 경우. 실제 소요 일수는 별도 반영 |
| 유급 업무 완료 | `energy -5`, `funds +5` | 보수가 있는 업무가 실제로 완료된 경우. 고정 현실 급여가 아님 |
| 비용이 드는 선택 확정 | `funds -5` | 선택 전에 자금 조건을 확인. 구체적 비용은 사건 설계에서 다르게 정할 수 있음 |
| 의미 있는 도움·협력 | 해당 NPC `relationship +3` | 그 NPC가 직접 경험하거나 전달받은 사건과 관계에 근거 |
| 의미 있는 갈등 | 해당 NPC `relationship -3` | 정당한 거절만으로 자동 하락하지 않음 |
| 관심을 직접 표현 | 해당 분야가 없으면 `50`으로 생성 | 이미 있으면 무조건 올리지 않는다. 단순 관심을 희망 직업 확정으로 바꾸지 않음 |
| 해당 활동을 실제로 경험하고 선호를 표현 | 해당 분야 `interests +5` 또는 `-5` | 선호·비선호가 명확할 때만. 침묵이나 체험 수행만으로 추정하지 않음 |

여러 효과가 적용되는 사건은 각 효과의 근거를 따로 남긴다. 활동 중 날짜를 보내는 경우 날짜를 더하고, 에너지 소모는 위 규칙에서 해당 활동 한 번만 적용한다. 하루를 보낸 사실만 기록하고 세부 활동의 소모가 없다면 `하루 활동`의 소모를 사용한다. 완료 여부나 3D 결과가 없으면 성공·실패·흥미를 추정하지 않는다.

## 5. 한계와 예외

- `funds`·`energy`·`ability`와 각 관계·흥미 수치는 변경 후 0~100으로 제한한다. 기록은 제안값이 아니라 검증 후 실제 반영값이다.
- `funds`가 0이면 비용이 필요한 선택은 진행할 수 없고 비용 없는 다른 행동을 선택할 수 있다. 부채·대출은 미정이다.
- `energy`가 0이면 에너지를 소모하는 활동은 시작할 수 없다. 휴식이나 에너지를 소모하지 않는 대화는 가능하다. 에너지 0을 죽음·질병으로 해석하지 않는다.
- `ability` 0은 해당 게임 지수의 최솟값일 뿐 현실 능력 부족을 뜻하지 않는다. `relationship` 0은 게임 관계 수치의 최솟값이며 관계 단절 여부는 별도 사건으로 정한다.
- `interests` 0은 그 분야의 기록된 관심 수치 최솟값이다. 관심 기록이 없는 것은 알 수 없다는 뜻이며 0과 구분한다.
- 사용자가 실제 건강·질병 정보를 먼저 말한 경우에도 게임 상태의 에너지에 자동 반영하거나 플레이어 기록에 저장하지 않는다. 위기 표현은 게임 자원 변경이 아니라 공통 안전 대응 경로에서 다룬다.

## 6. 추천 · NPC 기억과의 관계

- `interests`·실제 경험·사용자 목표는 추천의 근거 후보이며, 단일 수치만으로 직업 적성을 확정하지 않는다. 인생 중에도 기회를 제안하고 직업이 있으면 상대적으로 빈도를 낮춘다. 추천 빈도·임계값은 미정이다.
- 관계 지수와 NPC의 사건 기억은 별개다. 관계 수치가 바뀌었다는 사실만으로 다른 NPC가 사건을 알게 되지 않는다. NPC는 직접 들었거나 전달받아 기록된 정보만 안다.
- BGE-M3 검색은 백엔드가 허용한 해당 플레이·NPC의 기억 범위 안에서 수행하는 방향이다. 저장 모델과 접근 제어·실제 응답 시간은 별도 설계·검증이 필요하다.

## 7. 구현 전 확인과 검증

1. 백엔드·AI·프론트와 키 이름, 프로필과 상태의 경계, 각 값의 표시 및 검증 책임을 합의한다. 특히 현재 API의 `state` 예시·관계 변경 경로와 맞춰야 한다.
2. 정상 행동, 허용 범위 밖 변경, 0·100 경계, 자금 부족, 에너지 0, 이전 관심사 변경과 NPC별 정보 차단을 확인한다.
3. 동일 사건·3D 결과 재전송을 중복 반영하지 않고, 오류·중단과 미측정 결과를 성공·실패나 0으로 꾸미지 않는지 확인한다.
4. 짧은 플레이를 실제로 실행해 15분 권장 흐름과 수치 변화가 재미와 진행에 맞는지 측정한 뒤 초기값과 변화량을 조정한다.
5. 직업·준비 과정의 실제 근거, 건강·위기 대응, 나이별 진행·죽음 조건, NPC별 관계 초기화, 흥미 표시와 추천 빈도는 추가 확인한다.

> 게임 규칙 초안만 작성했다. API·DB·화면·모델에 구현되었거나 실제 플레이 테스트가 통과한 것은 아니다.
