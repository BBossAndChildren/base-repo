## 1. 개발 문서 구성을 3분할 구조에 맞춤 (2026-10-31)

### 결정
- 기능 번호를 백엔드 `BE`, AI 서버 `AI`, 웹 프론트 `FE` 로 나눈다 (기존 `B` · `F`)
- `03-api.md` 를 1부 프론트 ↔ 백엔드, 2부 백엔드 ↔ AI 서버로 나눈다
- `10-prompt-assembly.md` 를 추가해 `docs/game/` 문서 읽기 규칙 · 프롬프트 조립 순서 · 3D 빌드·에셋 추천 흐름을 모은다
- `02-architecture.md` · `06-deployment.md` · `08-checklist.md` 에 AI 서버와 3D 체험(Unity WebGL) 항목을 추가한다

### 근거
- 서비스가 웹 프론트 · 백엔드 · AI 서버 세 부분으로 나뉜다 ([00-idea.md 12. 서비스 구조](../00-idea.md#서비스-구조-회의-결정))
- 번호에 영역 이름을 그대로 써서 어느 쪽 기능인지 바로 알 수 있게 한다
- 게임 콘텐츠(`docs/game/`)는 시나리오 작가가, 그 문서를 읽어 프롬프트를 만드는 코드는 백엔드 담당이 맡는다. 두 역할이 한 문서만 보고 약속을 맞추도록 따로 둔다

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| 프롬프트 조립 내용을 `02` · `03` 에 나눠 적기 | 작가와 백엔드 담당이 여러 문서를 오가야 한다 |
| 웹 화면 문서(`05`)를 Unity 화면 문서로 교체 | 게임은 웹 화면에서 텍스트 채팅으로 진행하고 3D 는 분기에서만 쓴다 |

### 한계와 보완
- `docs/game/` 구조는 작가가 바꿀 수 있어, `10` 의 읽기 규칙은 구조가 바뀔 때마다 함께 맞춰야 한다
