## 1. 개발 문서 구성을 3분할 구조에 맞춤 (2026-10-31)

### 결정
- 기능 번호를 백엔드 `BE`, AI 서버 `AI`, 웹 프론트 `FE` 로 나눈다 (기존 `B` · `F`)
- `03-api.md` 를 1부 프론트 ↔ 백엔드, 2부 백엔드 ↔ AI 서버로 나눈다
- `10-prompt-assembly.md` 를 추가해 `docs/game/` 문서 읽기 규칙 · 프롬프트 조립 순서 · 3D 빌드·에셋 추천 흐름을 모은다
- `02-architecture.md` · `06-deployment.md` · `08-checklist.md` 에 AI 서버와 3D 체험(Unity WebGL) 항목을 추가한다

### 근거
- 서비스가 웹 프론트 · 백엔드 · AI 서버 세 부분으로 나뉜다 ([00-idea.md 12. 서비스 구조](../00-idea.md#서비스-구조-회의-결정))
- 번호에 영역 이름을 그대로 써서 어느 쪽 기능인지 바로 알 수 있게 한다
- 게임 콘텐츠(`docs/game/`)는 시나리오 작가가, 그 문서를 읽어 프롬프트를 만드는 코드는 백엔드 담당이 맡는다. 두 역할이 한 문서만 보고 약속을 맞추도록 따로 둔다

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| 프롬프트 조립 내용을 `02` · `03` 에 나눠 적기 | 작가와 백엔드 담당이 여러 문서를 오가야 한다 |
| 웹 화면 문서(`05`)를 Unity 화면 문서로 교체 | 게임은 웹 화면에서 텍스트 채팅으로 진행하고 3D 는 분기에서만 쓴다 |

### 한계와 보완
- `docs/game/` 구조는 작가가 바꿀 수 있어, `10` 의 읽기 규칙은 구조가 바뀔 때마다 함께 맞춰야 한다

## 2. 3D 체험 결과 전달: 즉시 전달 + 종료 시 반영 (2026-10-31)

### 결정
- 프론트는 Unity 응답을 받을 때마다 빌드·방·시나리오 정보를 덧붙여 즉시 백엔드로 보낸다 (변경: 에셋 → 방·시나리오, 결정 4)
- 백엔드는 이벤트를 쌓기만 하고, `experience.ended` 를 받으면 한 번 플레이어 기록에 반영한다
- 종료 응답이 오지 않으면 그때까지 받은 이벤트로 "중간에 그만둠" 처리한다
- **변경 (2026-10-31):** 재전송은 "최대 3회" 대신 Unity 연결 코드의 전송 큐 규칙(저장 확인까지 2초마다)을 따른다. 종료 응답이 없는 체험은 "재개 시 처리" 대신 Unity 명세 v003 정산(새 체험 시작 때, heartbeat 30초 · lease 120초)을 따른다 (결정 9)

### 근거
- 체험 도중 멈추거나 탭을 닫으면 프론트에만 있던 결과가 사라진다. 백엔드가 최종 목적지이므로 받는 즉시 넘긴다
- 플레이어 기록을 이벤트마다 다시 쓰면 무겁고, 거의 동시에 도착한 요청이 서로 덮어쓸 수 있다

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| B. 매번 즉시 보내고 백엔드도 매번 플레이어 기록 수정 | 덮어쓰기 · 중복 반영을 백엔드가 따로 막아야 한다 |
| C. 체험이 끝날 때 한 번만 보냄 | 도중에 멈추면 결과를 잃는다 |

### 한계와 보완
- Unity 명세 v001 에서 실시간 이벤트 전달은 선택 기능이다. Unity 가 이를 구현하기 전까지는 종료 응답 한 번만 받을 수 있다 
- **변경 (2026-10-31):** Unity 담당이 물건 상태가 바뀔 때마다 실시간으로 보내기로 확정했다. 실시간 이벤트 형식은 다음 명세 버전에서 받는다 ([11 F2](11-open-issues.md#f-확인이-필요한-질문))

## 3. 공통 지침 문서와 플레이어 기록 분리 (2026-10-31)

### 결정
- 시나리오 · 가이드라인(세이프가드)은 모든 유저가 공통으로 쓰는 문서로 백엔드 서버 한곳에 두고, AI 서버에 요청할 때마다 반드시 함께 보낸다
- 나이 · 인적 정보 · 게임 상태 · 3D 체험 결과는 플레이어별 기록으로 백엔드 DB 에 둔다 (예: Supabase, 종류는 바꿀 수 있음)

### 근거
- 지침 문서는 게임이 범위를 벗어나지 않게 하는 하네스라 모든 유저에게 같아야 한다
- 플레이어 정보는 사람마다 달라, 공통 문서를 고치면 다른 플레이어에게 섞이고 동시 수정 시 덮어쓰인다

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| 체험 결과로 공통 마크다운을 직접 수정 | 다른 플레이어에게 결과가 섞이고 동시에 고치면 내용이 사라진다 |

### 한계와 보완
- DB 종류는 아직 정하지 않았다 ([11 A1](11-open-issues.md#a-스펙-미확정-항목))

## 4. 3D 체험은 방 · 시나리오만 고름 (2026-10-31)

### 결정
- AI 는 에셋을 고르지 않고 빌드 · 방(`roomId`) · 시나리오(`scenarioId`) 만 추천한다
- 백엔드 카탈로그 JSON 은 빌드 → 방 → 직업별 시나리오 목록 구조로 둔다

### 근거
- Unity 는 같은 방에서 공유 에셋을 쓰되, 상호작용을 위해 직업별 장면을 시나리오로 미리 구성해 WebGL 로 보여 준다. 시나리오를 고르면 에셋이 정해진다 (Unity 담당 확인)
- Unity 명세의 시작 호출도 `roomId` · `scenarioId` · `scenarioVersion` 만 받는다

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| AI 가 에셋까지 골라 Unity 에 전달 | Unity 쪽에 에셋 지정 기능이 없고 필요하지 않다 |

### 한계와 보완
- 직업마다 장면이 달라야 하면 Unity 쪽에서 그만큼 시나리오를 만들어야 한다

## 5. 빌드 파일은 주소로 전달 (2026-10-31)

### 결정
- 백엔드는 빌드 파일을 정해진 위치에 올려 두고, 채팅 응답에 빌드 주소(`buildUrl`)를 준다. 프론트가 그 주소로 불러온다

### 근거
- Unity WebGL 빌드는 `.wasm` · `.data` · 로더 등 여러 파일이고 수십 MB 라 API 응답에 직접 담으면 느리고 깨지기 쉽다
- 프론트가 실제 빌드 파일을 받는다는 원래 의도는 그대로 지켜진다

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| API 응답에 빌드 파일을 직접 담기 | 여러 파일 · 큰 용량을 한 응답으로 보내기 어렵다 |

### 한계와 보완
- 빌드를 올려 둘 위치(정적 호스팅 등)는 배포 설계 때 정한다 ([06-deployment.md](06-deployment.md))

## 6. AI 응답을 정해진 JSON 으로 받음 (2026-10-31)

### 결정
- AI 서버는 대사 · 상태 변경 제안 · 3D 분기 여부 · 인생 종료 여부를 정해진 JSON 으로 응답한다
- 상태 변경은 제안이며, 백엔드가 가이드라인과 현재 상태로 확인한 뒤 반영한다

### 근거
- 자유 글에서 상태 변경을 뽑아내면 틀리기 쉽다. 정해진 형식이면 백엔드가 "말만으로 직업이 바뀌는" 변경을 걸러 낼 수 있다

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| 자유 글 응답 후 백엔드가 해석 | 상태 변경을 정확히 뽑기 어렵고 검사가 불안정하다 |

### 한계와 보완
- 모델이 형식을 어길 수 있어 1회 재요청 후 실패 시 오류로 안내한다

## 7. 게임 시작 입력 항목 (2026-10-31)

### 결정
- 필수: 이름 · 나이 · 현재 상황 · 희망 직업 유무(있으면 직업명)
- 선택: 성별 · 관심사 · 전공·학년 · 잘하는 것 · 가치관 · 롤모델 · MBTI
- 받지 않음: 건강 · 질병 · 가족관계 · 반려동물 · 성장과정 · 습관 · 버킷리스트

### 근거
- 한 번의 플레이 권장 시간이 약 15분이라 시작 입력이 길면 게임 전에 지친다. 필수는 게임 시작에 꼭 필요한 것만 둔다
- 건강 · 질병은 개인정보보호법상 민감정보라 받지 않는다
- 가족 · 주변 인물은 게임이 랜덤으로 구성한다 ([00-idea.md 7장](../00-idea.md#7-주변-인물과-랜덤성)). 입력으로 받으면 이 설계와 겹친다
- 관심사 · 잘하는 것 · 가치관은 AI 가 첫 사건과 추천 방향을 정하는 데 쓸 수 있다

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| 성장과정 · 습관 · 버킷리스트 입력 | 긴 글 입력이라 시작이 늦어진다. 필요하면 게임 안 대화에서 자연스럽게 묻는다 |
| 건강 · 질병 입력 | 민감정보 |

### 한계와 보완
- 선택 항목이 AI 응답에 실제로 도움이 되는지는 플레이 테스트로 확인한다
- **변경 (2026-10-31):** 선택 항목은 시작 때 랜덤 2개만 보여 주고(건너뛰기 가능), 나머지는 게임 중 NPC 가 대화로 하나씩 묻는다. 건강 · 질병은 받지 않을 뿐 아니라 AI 가 묻거나 유도하지도 않는다

## 8. 3D 빌드 파일 위치 (2026-10-31)

### 결정
- 빌드 파일은 백엔드 서버 폴더(`/srv/builds/<buildId>/`)에 두고, Django 앞의 Nginx 가 `/builds/` 주소로 내려준다
- 빌드 파일은 Git 저장소에 넣지 않고 배포 때 서버로 복사한다. 저장소에는 빌드 카탈로그 JSON 만 둔다

### 근거
- Django(Gunicorn)로 수십 MB 파일을 보내면 그동안 worker 가 묶여 채팅 요청이 밀린다
- GitHub 은 50MB 이상 파일에 경고, 100MB 이상은 차단하고, 빌드를 바꿀 때마다 저장소가 커진다

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| Django 가 직접 내려주기 | worker 가 묶인다 |
| 백엔드 저장소 안 빌드 폴더 | GitHub 용량 제한 · 저장소 비대화 |
| 네이버 클라우드 Object Storage | 가능하지만 설정이 더 많다. 사용자가 늘면 다시 검토 |

### 한계와 보완
- Unity WebGL 용 헤더 설정이 필요하며 압축 방식에 따라 다르다 ([06 5-1](06-deployment.md#5-1-백엔드-서버-처음-세팅)). 현재 테스트 빌드는 비압축이다
- 프론트가 https 이므로 백엔드 서버에 도메인 · SSL 인증서가 필요하다

---

- **변경 (2026-11-01, 결정 27):** 빌드 폴더 `/srv/builds/` 는 GPU 단일 서버에 둔다. 게이트웨이(`backend/deploy/`)가 내려준다

## 10. 배포 · SSL · CORS 담당 (2026-10-31)

### 결정
- 웹 프론트는 Vercel (SSL 자동). 백엔드는 네이버 클라우드 서버에서 Nginx + Let's Encrypt 로 SSL 처리
- API CORS 는 Django(django-cors-headers)만 붙인다. 빌드 iframe 은 Nginx `frame-ancestors` 로 프론트 주소만 허용

### 근거
- 프론트가 https 라 백엔드 · 빌드도 https 가 아니면 브라우저가 막는다
- CORS 헤더를 Nginx 와 Django 가 함께 붙이면 중복 헤더로 브라우저가 거부한다
- Unity 연결 코드가 빌드를 iframe 으로 열기 때문에, 빌드 쪽은 CORS 가 아니라 frame-ancestors 가 필요하다

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| 프론트 Railway | 가능하지만 정적 프론트에는 Vercel 이 더 간단 |
| Nginx 에서 CORS 처리 | Django 와 중복 위험, 설정이 두 곳으로 나뉜다 |

### 한계와 보완
- 백엔드 도메인이 있어야 SSL 을 받을 수 있다 ([11 F4](11-open-issues.md#f-확인이-필요한-질문))

---

- **변경 (2026-11-01, 결정 27):** 공개 대상 서버가 GPU 서버로 바뀐다. 터널 · CORS 담당 원칙(Cloudflare Tunnel, CORS 는 Django + 게이트웨이 허용 출처)은 유지하고, AI 는 같은 서버 내부 호출이라 별도 터널을 쓰지 않는다

## 11. 백엔드 프로젝트 초기 설정 (2026-10-31)

### 결정
- 사용자 지정 Django · DRF · PostgreSQL 스택을 `backend/`에 구성한다. 설정은 `config/`, 공통 API는 `apps/core/`에 둔다.
- Python 3.12와 Django 5.2 LTS를 사용하며 Python 의존성은 `uv.lock`으로 고정한다.
- 상태 확인 API · Swagger · CORS · Gunicorn WSGI 설정부터 준비하고, 게임 모델과 AI 호출은 별도 구현한다.

### 근거
- 프론트 · AI 서버와 독립된 실행 환경이 필요하며 실제 PostgreSQL 연결부터 검증해야 한다.
- 로그인 없는 게스트 설계이므로 현 단계에서는 Django 사용자 · 관리자 테이블을 만들 필요가 없다.

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| SQLite로만 세팅 검증 | 운영 예정 DB와 다르므로 PostgreSQL 연결 오류를 확인하지 못함 |
| 게임 모델과 AI 호출까지 함께 구현 | 이번 요청은 명세 구현 전 실행 기반 준비이며 DB 설계도 아직 미확정 |

### 한계와 보완
- AI · 직업 JSON · 시나리오 파일 · Unity 빌드는 실제로 연결하지 않았다. Swagger는 구현된 상태 확인 API만 보여 준다.
- 네이버 클라우드 서버 · 운영 DB · 도메인 · HTTPS 구성은 실제 배포 작업에서 검증한다.

## 12. 기존 백엔드 스택 컨테이너화 (2026-10-31)

### 결정
- Django · DRF · HTTPX · PostgreSQL · Gunicorn WSGI와 기존 uv.lock을 유지한다.
- 기본 Compose는 Gunicorn과 PostgreSQL을 실행하고 개발 설정에서만 자동 새로고침과 소스 연결을 사용한다.
- Nginx · HTTPS는 기존 호스트 설치, AI는 별도 GPU 서버 방식을 유지한다.

### 근거
- 사용자가 기존 기술 스택을 유지한 컨테이너 구성을 요청했다. 단일 서버에서 실행 환경을 재현하고 DB 준비 순서를 명시할 수 있다.

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| 프레임워크 · 앱 서버 방식 변경 | 사용자 지정 스택과 다르며 컨테이너화에 필요하지 않음 |
| 개발 소스를 운영 컨테이너에 연결 | 배포된 이미지와 실제 실행 코드가 달라질 수 있음 |

### 한계와 보완
- 호스트 PostgreSQL 데이터는 별도 보존하며 컨테이너 DB로 자동 이전하지 않는다.
- 운영 DB 계정 · 백업 · 도메인 · HTTPS는 배포 때 검증한다. 게임 API나 AI 요청 구현 범위는 늘리지 않는다.

## 14. 3D 연동 API 를 Unity 어댑터에 맞춤 (2026-10-31)

### 결정
- 이벤트 API 는 Unity 이벤트를 **원본 그대로** 받는다 (`/plays/{playId}/experience-events`). 이전의 `{buildId, …, unityEvent}` 감싸기는 없앤다
- 3D 연동 API 4개(이벤트 · 정산 · 생존 신호 · 미수신 기록)는 응답을 `{code, data}` 로 감싸지 않는다
- 프론트는 어댑터를 `credentials: 'omit'` · `X-Player-Id` 헤더로 만든다
- 종료 응답 미수신 기록 API(1-10)를 추가한다

### 근거
- Unity 담당의 `frontend/backend.js` 는 이벤트를 그대로 보내고 응답 본문을 그대로 읽는다. 이벤트 안에 빌드 · 방 · 시나리오 ID 가 이미 있다
- 어댑터 기본값 `credentials: 'include'` 는 쿠키를 보내는데 우리는 쿠키를 쓰지 않아 CORS 에서 막힌다
| 어댑터를 고쳐 우리 형식에 맞춤 | Unity 담당 원본을 고치면 다음 전달 때마다 다시 고쳐야 한다 |

### 한계와 보완
- 공통 응답 형식에 예외가 생긴다. 03 공통 규약에 예외를 명시했다

## 17. 모노레포: base-repo 에 frontend · backend · docs (2026-10-31)

### 결정
- `base-repo` 하나에 `frontend/` · `backend/` · `docs/` 를 둔다. AI 서버 코드는 별도 저장소로 둔다
- 라벨 · 커밋 scope: `frontend/` = `fe`, `backend/` 와 AI 서버 작업 = `be`
- Unity 연결 코드(`docs/unity/frontend/`)는 코드 작성 때 참고만 하고 `frontend/` 안으로 복사 · 배치하지 않는다
- `frontend/` · `backend/` 에 각자 `AGENTS.md` · `CLAUDE.md` 를 두어 AI 코딩 도구가 꼭 읽을 문서를 지정한다

### 근거
- 팀원이 Claude · GPT 같은 AI 코딩 도구로 개발한다. 이 도구들은 열려 있는 저장소의 파일만 읽으므로, 설계 문서가 같은 저장소에 있어야 매번 최신 문서를 기준으로 작업한다
- 문서 복사 · 동기화가 필요 없어 문서가 갈라지지 않는다

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| 프론트 · 백 별도 저장소 + 링크 | AI 도구가 다른 저장소 문서를 읽지 않는다 |

## 23. Unity 연결 코드는 빌드에서 실행 시 불러온다 (2026-10-31)

### 결정
- 프론트는 Unity 연결 코드(`client.js` 의 `createExperienceClient` · `createOutbox`)를 저장소에 복사하지 않고, 빌드에 함께 들어 있는 `<buildUrl>/frontend/client.js` 를 실행할 때 `import()` 로 불러와 쓴다
- 우리 백엔드 API 호출(이벤트 · 정산 · 생존 신호 · 미수신 기록)은 프론트가 직접 작성한다
- 배포 서버는 `/builds/` 에 프론트 주소 CORS 허용 헤더를 붙인다

### 근거
- 연결 코드는 핸드셰이크 · 출처 확인 · 중복/순서 충돌 · 누적 스냅샷 · 요청 재전송 · 5초 미확인 처리 등 약 300줄의 정교한 규칙이다. 다시 작성하면 Unity 쪽과 어긋날 위험이 크다
- 최종 빌드(`career-suite-integration-v005`)에 연결 코드가 함께 들어 있어, 불러 쓰면 빌드와 버전이 항상 같다
- "`frontend/` 로 복사하지 않는다"는 이전 결정(결정 17)도 지킨다
- 실제 최종 빌드로 시작 → 체험 → 종료 · 이벤트 저장 확인을 headless Chrome 으로 확인했다 (PR #49)

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| 연결 코드를 TypeScript 로 다시 작성 | Unity 규칙과 어긋날 위험, 버전이 오를 때마다 따라 고쳐야 함 |
| 연결 코드를 `frontend/` 에 복사 | 결정 17 위반, 빌드와 버전이 갈라짐 |

### 한계와 보완
- 빌드 서버에 CORS 설정이 없으면 3D 체험을 불러오지 못한다 (06 5-1 ⑤ · 트러블슈팅)
- 연결 코드에 타입이 없어 프론트가 최소 타입(`frontend/src/types/unity.ts`)을 둔다. 규격이 바뀌면 함께 맞춘다

## 24. 인생·직업 상세 기획과 연동 책임 갱신 (2026-10-31)

### 결정
- [게임 상세 기획](../game/06-life-career-design.md)을 대화로 확정한 최신 기획 문서로 둔다. 기존 03-rules의 추상 자금 지수 설명은 최신 문서 안내로 대체한다.
- AI는 이야기와 변화를 제안하고 백엔드는 상태·사건·기억의 공개 범위를 검증한 뒤 확정한다. 프론트는 확정 결과를 표시한다.
- 직업 지식 검색에 BGE-M3를 사용하고, NPC 기억은 플레이와 인물별로 제한한다. 배경 정보 전달과 감정·해석은 구분해 기록한다.
- 원화 자금·빚·미납·주거·건강·에너지·스트레스·성장과 월별 정산을 반영한다. 중요한 선택은 기간 압축 중에도 넘기지 않는다.
- 턴 요청 ID와 상태 버전으로 중복 적용·과거 상태 덮어쓰기를 막고, 실패한 턴은 상태를 변경하지 않는다. 마지막 확정 지점에서 재개한다.

### 근거
사용자가 NPC의 성격·정보 경계, 현실적인 비용과 선택권, 핵심 업무 경험, 실제 화면 연동 책임을 함께 확정했다.

### 버린 대안
| 대안 | 버린 이유 |
|---|---|
| 추상 자금 0~100과 자동 마이너스 | 실제 원화 지출과 부족할 때의 선택을 표현하지 못함 |
| 모든 NPC에게 전체 대화 전달 | 인물별로 알 수 있는 사실의 경계를 없앰 |
| 매 턴 NPC끼리 자동 대화 | 불필요한 대화와 처리량 증가 |
| AI 제안을 즉시 저장·표시 | 규칙 위반과 재시도 중복 적용 가능 |

### 한계
이 변경은 문서 설계다. 기존 백엔드·프론트 코드와 API가 모두 구현되었다는 의미가 아니다. 원화 상태·기억·턴 확정·일시정지 계약은 각 담당 구현에 함께 반영해야 한다.

## 26. 인트로 디자인 토큰으로 전체 디자인 교체 (2026-11-01)

- 앱 화면은 역할 변수(`--color-*`)를 쓰고, 역할 변수가 토큰을 가리킨다. 토큰에 없는 역할(카드 면 · 보조 면 · 선택 칩)은 토큰의 반투명 색을 배경 위에 섞어 불투명 값으로 만들고, 상태색(오류 `#ff8a80` · 주의 `#f2c879`) · 비활성 글자 · 모달 뒤 어둡게만 새로 정했다. 모두 AA 이상 ([docs/design/README.md](../design/README.md#명도-대비-wcag-21-계산값))
- 글꼴은 토큰의 Pretendard 를 jsDelivr CDN 고정 버전으로 불러온다
- 인트로는 토큰 버전(v002, `tokens` prop) 으로 바꾼다. 화면 모습은 v001 과 같다
- 3D 체험 Unity 배경색도 `--color-bg` (`#101e24`) 로 맞춘다

### 근거
- 사용자가 새 디자인 파일을 전달하고 전체 디자인 교체를 요청했다
- 인트로 → 시작 화면이 같은 색 · 글꼴로 이어져야 첫 화면에서 끊기지 않는다
- 토큰을 원본으로 두면 Unity 담당이 값을 바꿔도 생성만 다시 하면 된다

### 버린 대안
| 대안 | 버린 이유 |
|---|---|
| 기존 크림색 앱 + 인트로만 어두운 화면 | 인트로가 끝나고 시작 화면에서 분위기가 완전히 바뀜 |
| 앱 화면이 `--ci-*` 를 직접 사용 | 인트로 전용 이름(`gate` · `film` 등)이 화면 코드에 퍼지고 토큰 변경 영향을 추적하기 어려움 |
| 상태색도 토큰 안에서만 고르기 | 토큰에 빨강 · 노랑 계열이 없어 오류 · 주의를 구분할 수 없음 |
| `docs/design/` 를 빌드에서 직접 읽기 | Vercel Root Directory 가 `frontend/` 라 폴더 밖 파일에 의존하게 됨 |

### 한계와 보완
- `tokens.json` 이 두 곳(전달물 보관 · 코드 사본)에 있다. 새 전달물이 오면 둘을 함께 바꾼다 (docs/design/README.md 절차)
- 새로 정한 상태색 · 섞은 면 색은 토큰에 없다. Unity 담당에게 다음 토큰 판에 앱용 semantic 값 추가를 요청할 수 있다
- Pretendard 는 외부 CDN 이라 막히면 시스템 글꼴로 보인다

## 27. GPU 서버 한 대에서 운영 (2026-11-01)

### 결정
- Django 게임 백엔드 · PostgreSQL · Qwen AI API · 정적 에셋 게이트웨이 · Cloudflare Tunnel 을 **GPU 서버 한 대**에서 운영한다. 별도의 일반 백엔드 서버는 쓰지 않는다 (팀 합의, 설계 정리 #100 · PR #103)
- 프론트 ↔ 백엔드 API 계약, 게임 저장 · 검증 책임(Django), 역할 분담(백엔드 · AI 담당)은 그대로다. AI API 는 외부에 공개하지 않고 Django 가 같은 서버의 내부 주소로 호출한다
- 공개는 게이트웨이(`/api/` · `/builds/` · `/intro-assets/`)만 터널로 한다

### 근거
- 서버 두 대 사이의 사설망 접속(11 F9)과 AI 전용 터널 · 내부 키 노출 위험을 없앤다
- 운영할 서버가 하나라 해커톤 기간에 배포 · 점검 단계가 줄어든다

### 버린 대안
| 대안 | 버린 이유 |
|---|---|
| 일반 서버(Django · DB) + GPU 서버(AI) 두 대 (이전 결정 10) | 서버 간 네트워크 확인과 터널 · 키 관리가 추가로 필요 |
| AI API 를 터널로 공개하고 백엔드가 외부 주소로 호출 | 내부 API 가 외부에 노출됨 |

### 한계와 보완
- 서버 한 대 장애가 게임 API · DB · 추론에 함께 영향을 준다. 백업 · 복구 · 재시작 정책을 운영 전에 검증한다
- 단일 GPU 는 한 번에 한 추론만 처리해 겹친 요청은 503 이 될 수 있다. 사용자 수 · 대기 정책은 성능 측정 후 정한다
- 이식 · 연동은 아직 검증 전이다 (06 0절 단계표). 서버 접속 방법 · 내부 포트 · 터널 도메인은 11 F7 로 확정한다
- 이전 두 서버 배포 절차는 06 에 "이전 배포안" 으로 남겨 두었다. 서버 공통 절차(Docker · 게이트웨이 · `/srv/builds` · `/srv/intro-assets` · 터널)는 GPU 서버에서 같은 방식으로 쓴다

### 보완 (2026-11-01, 실제 배포)
- AI API 는 AI 담당이 호스트 Python 으로 `127.0.0.1:8010` 에 띄워 운영한다. 백엔드 컨테이너는 Docker 내부망에만 열린 중계기(`ai-relay`, `172.17.0.1:18010`)를 거쳐 `host.docker.internal` 로 호출한다 (#113 · #115). AI 를 처음부터 `172.17.0.1` 로 띄우면 중계기 없이 쓸 수 있다
- 터널은 quick tunnel 을 `--protocol http2` 로 쓴다 (서버의 UDP 차단). 주소가 재실행 때마다 바뀌는 한계는 고정 도메인(named tunnel)을 정하면 없앨 수 있다 (11 F7)
- 프론트 출처는 `https://base-repo-zeta.vercel.app` 하나만 허용한다 (#122). Cloudflare 가 502 · 504 를 바꾸는 문제는 프론트가 채팅 중 네트워크 오류를 응답 지연으로 안내해 대응한다 (#121)

## 28. 결말 = 살아온 인생 회고, AI 없으면 백엔드 생성 (2026-11-01)

### 결정
- 캐릭터가 사망하면 **살아온 인생을 읊어 주며 끝난다**. 회고 뒤에 기존처럼 추천 직업 3개(새 직업 1개 이상)를 보여 준다
- AI 결말 API(`/ai/v1/ending`)가 없거나 실패 · 시간 초과면 백엔드가 저장된 기록(상태 · 사건 · 체험 · 대화)으로 회고와 추천을 만든다 (`generatedBy: "backend"`). AI 결말이 생기면 다음 조회 때 AI 결말로 교체한다

### 근거
- 사용자가 결말 방향을 확정했다. AI 서버에 결말 API 가 아직 없어 결말 화면이 오류가 났다
- 회고는 이미 저장된 사실로 만들 수 있어 AI 없이도 정확하다

### 버린 대안
| 대안 | 버린 이유 |
|---|---|
| 회고만 보여 주고 추천 직업 제거 | 서비스 목적(진로 탐색 · 다음 경험 제안)이 사라짐 |
| AI 결말 API 가 생길 때까지 기다림 | 그 전까지 결말 화면이 오류 |

### 한계와 보완
- 백엔드 회고는 문장이 단조롭고, 하는 일은 3D 체험 설명이나 직업백과 안내에 그친다 (RAG 근거 없음)
- 사망하지 않으면 결말이 오지 않는다 (15분은 권장 시간, 결정 22)

## 30. 건강 자연 회복 (2026-11-01)

### 결정
- 스트레스 50 미만이고 과로 상태가 아닌 날을 **회복일**로 쌓는다. 일반 날 1일, 휴일 2일, 휴가일 3일로 센다
- 회복일 30일마다 건강 +2 (`healthRecovered` 사건). 조건이 깨지면 쌓인 회복일은 0 으로
- **회복 상한** = 80(시작 건강) − 65세부터 현재 나이까지의 노화 감소 합 (결정 29). 65세 77 · 70세 62 · 75세 44 · 80세 14 · 83세 이상 0. 상한보다 높은 건강을 깎지는 않는다
- 건강 0 에서도 회복할 수 있다. 1 이상이 되면 "건강 0 연속 6개월" 기간이 초기화된다 (06 7절)

### 근거
- 건강을 줄이는 규칙(높은 스트레스 · 노화)만 있어 한 번 나빠지면 되돌릴 방법이 없었다
- 상한을 나이로 계산하면 늙어서 시작한 인생도 노화 결말에 닿는다 (회복이 노화를 상쇄하지 못함)

### 버린 대안
| 대안 | 버린 이유 |
|---|---|
| 상한 없이 회복 | 1년에 최대 +24(휴가만 쓰면 더) 라 65세 이후 노화(−3~−20/년)를 상쇄해 죽지 않게 됨 |
| 지금까지 받은 노화 감소를 기록해 상한 계산 | 늙은 나이로 시작한 인생은 기록이 없어 상한이 80 이 됨 |

### 한계와 보완
- 병원 치료 · 의료비 같은 적극적인 회복 행동은 아직 없다 (쓰러짐 뒤 에너지 회복만 있음)
- 값은 플레이해 보며 조정한다
