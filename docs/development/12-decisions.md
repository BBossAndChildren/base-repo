| 10 | 프론트 Vercel, 백엔드는 Cloudflare Tunnel(SSL 자동), CORS 는 Django 가 담당 | 제공 서버가 사설 IP · VPN 전용이라 도메인 · 인증서를 쓸 수 없음 |
| 11 | 3D 연동 API 를 Unity 어댑터에 맞춤 | 이미 만들어진 연결 코드를 그대로 쓰기 위해 |

## 1. 개발 문서 구성을 3분할 구조에 맞춤 (2026-10-31)

### 결정
- 기능 번호를 백엔드 `BE`, AI 서버 `AI`, 웹 프론트 `FE` 로 나눈다 (기존 `B` · `F`)
- `03-api.md` 를 1부 프론트 ↔ 백엔드, 2부 백엔드 ↔ AI 서버로 나눈다
- `10-prompt-assembly.md` 를 추가해 `docs/game/` 문서 읽기 규칙 · 프롬프트 조립 순서 · 3D 빌드·에셋 추천 흐름을 모은다
- `02-architecture.md` · `06-deployment.md` · `08-checklist.md` 에 AI 서버와 3D 체험(Unity WebGL) 항목을 추가한다

### 근거
- 서비스가 웹 프론트 · 백엔드 · AI 서버 세 부분으로 나뉜다 ([00-idea.md 12. 서비스 구조](../00-idea.md#서비스-구조-회의-결정))
- 번호에 영역 이름을 그대로 써서 어느 쪽 기능인지 바로 알 수 있게 한다
- 게임 콘텐츠(`docs/game/`)는 시나리오 작가가, 그 문서를 읽어 프롬프트를 만드는 코드는 백엔드 담당이 맡는다. 두 역할이 한 문서만 보고 약속을 맞추도록 따로 둔다

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| 프롬프트 조립 내용을 `02` · `03` 에 나눠 적기 | 작가와 백엔드 담당이 여러 문서를 오가야 한다 |
| 웹 화면 문서(`05`)를 Unity 화면 문서로 교체 | 게임은 웹 화면에서 텍스트 채팅으로 진행하고 3D 는 분기에서만 쓴다 |

### 한계와 보완
- `docs/game/` 구조는 작가가 바꿀 수 있어, `10` 의 읽기 규칙은 구조가 바뀔 때마다 함께 맞춰야 한다

## 2. 3D 체험 결과 전달: 즉시 전달 + 종료 시 반영 (2026-10-31)

### 결정
- 프론트는 Unity 응답을 받을 때마다 빌드·방·시나리오 정보를 덧붙여 즉시 백엔드로 보낸다 (변경: 에셋 → 방·시나리오, 결정 4)
- 백엔드는 이벤트를 쌓기만 하고, `experience.ended` 를 받으면 한 번 플레이어 기록에 반영한다
- 종료 응답이 오지 않으면 그때까지 받은 이벤트로 "중간에 그만둠" 처리한다
- **변경 (2026-10-31):** 재전송은 "최대 3회" 대신 Unity 연결 코드의 전송 큐 규칙(저장 확인까지 2초마다)을 따른다. 종료 응답이 없는 체험은 "재개 시 처리" 대신 Unity 명세 v003 정산(새 체험 시작 때, heartbeat 30초 · lease 120초)을 따른다 (결정 9)

### 근거
- 체험 도중 멈추거나 탭을 닫으면 프론트에만 있던 결과가 사라진다. 백엔드가 최종 목적지이므로 받는 즉시 넘긴다
- 플레이어 기록을 이벤트마다 다시 쓰면 무겁고, 거의 동시에 도착한 요청이 서로 덮어쓸 수 있다

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| B. 매번 즉시 보내고 백엔드도 매번 플레이어 기록 수정 | 덮어쓰기 · 중복 반영을 백엔드가 따로 막아야 한다 |
| C. 체험이 끝날 때 한 번만 보냄 | 도중에 멈추면 결과를 잃는다 |

### 한계와 보완
- Unity 명세 v001 에서 실시간 이벤트 전달은 선택 기능이다. Unity 가 이를 구현하기 전까지는 종료 응답 한 번만 받을 수 있다 
- **변경 (2026-10-31):** Unity 담당이 물건 상태가 바뀔 때마다 실시간으로 보내기로 확정했다. 실시간 이벤트 형식은 다음 명세 버전에서 받는다 ([11 F2](11-open-issues.md#f-확인이-필요한-질문))

## 3. 공통 지침 문서와 플레이어 기록 분리 (2026-10-31)

### 결정
- 시나리오 · 가이드라인(세이프가드)은 모든 유저가 공통으로 쓰는 문서로 백엔드 서버 한곳에 두고, AI 서버에 요청할 때마다 반드시 함께 보낸다
- 나이 · 인적 정보 · 게임 상태 · 3D 체험 결과는 플레이어별 기록으로 백엔드 DB 에 둔다 (예: Supabase, 종류는 바꿀 수 있음)

### 근거
- 지침 문서는 게임이 범위를 벗어나지 않게 하는 하네스라 모든 유저에게 같아야 한다
- 플레이어 정보는 사람마다 달라, 공통 문서를 고치면 다른 플레이어에게 섞이고 동시 수정 시 덮어쓰인다

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| 체험 결과로 공통 마크다운을 직접 수정 | 다른 플레이어에게 결과가 섞이고 동시에 고치면 내용이 사라진다 |

### 한계와 보완
- DB 종류는 아직 정하지 않았다 ([11 A1](11-open-issues.md#a-스펙-미확정-항목))

## 4. 3D 체험은 방 · 시나리오만 고름 (2026-10-31)

### 결정
- AI 는 에셋을 고르지 않고 빌드 · 방(`roomId`) · 시나리오(`scenarioId`) 만 추천한다
- 백엔드 카탈로그 JSON 은 빌드 → 방 → 직업별 시나리오 목록 구조로 둔다

### 근거
- Unity 는 같은 방에서 공유 에셋을 쓰되, 상호작용을 위해 직업별 장면을 시나리오로 미리 구성해 WebGL 로 보여 준다. 시나리오를 고르면 에셋이 정해진다 (Unity 담당 확인)
- Unity 명세의 시작 호출도 `roomId` · `scenarioId` · `scenarioVersion` 만 받는다

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| AI 가 에셋까지 골라 Unity 에 전달 | Unity 쪽에 에셋 지정 기능이 없고 필요하지 않다 |

### 한계와 보완
- 직업마다 장면이 달라야 하면 Unity 쪽에서 그만큼 시나리오를 만들어야 한다

## 5. 빌드 파일은 주소로 전달 (2026-10-31)

### 결정
- 백엔드는 빌드 파일을 정해진 위치에 올려 두고, 채팅 응답에 빌드 주소(`buildUrl`)를 준다. 프론트가 그 주소로 불러온다

### 근거
- Unity WebGL 빌드는 `.wasm` · `.data` · 로더 등 여러 파일이고 수십 MB 라 API 응답에 직접 담으면 느리고 깨지기 쉽다
- 프론트가 실제 빌드 파일을 받는다는 원래 의도는 그대로 지켜진다

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| API 응답에 빌드 파일을 직접 담기 | 여러 파일 · 큰 용량을 한 응답으로 보내기 어렵다 |

### 한계와 보완
- 빌드를 올려 둘 위치(정적 호스팅 등)는 배포 설계 때 정한다 ([06-deployment.md](06-deployment.md))

## 6. AI 응답을 정해진 JSON 으로 받음 (2026-10-31)

### 결정
- AI 서버는 대사 · 상태 변경 제안 · 3D 분기 여부 · 인생 종료 여부를 정해진 JSON 으로 응답한다
- 상태 변경은 제안이며, 백엔드가 가이드라인과 현재 상태로 확인한 뒤 반영한다

### 근거
- 자유 글에서 상태 변경을 뽑아내면 틀리기 쉽다. 정해진 형식이면 백엔드가 "말만으로 직업이 바뀌는" 변경을 걸러 낼 수 있다

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| 자유 글 응답 후 백엔드가 해석 | 상태 변경을 정확히 뽑기 어렵고 검사가 불안정하다 |

### 한계와 보완
- 모델이 형식을 어길 수 있어 1회 재요청 후 실패 시 오류로 안내한다

## 7. 게임 시작 입력 항목 (2026-10-31)

### 결정
- 필수: 이름 · 나이 · 현재 상황 · 희망 직업 유무(있으면 직업명)
- 선택: 성별 · 관심사 · 전공·학년 · 잘하는 것 · 가치관 · 롤모델 · MBTI
- 받지 않음: 건강 · 질병 · 가족관계 · 반려동물 · 성장과정 · 습관 · 버킷리스트

### 근거
- 한 번의 플레이가 최대 15분이라 시작 입력이 길면 게임 전에 지친다. 필수는 게임 시작에 꼭 필요한 것만 둔다
- 건강 · 질병은 개인정보보호법상 민감정보라 받지 않는다
- 가족 · 주변 인물은 게임이 랜덤으로 구성한다 ([00-idea.md 7장](../00-idea.md#7-주변-인물과-랜덤성)). 입력으로 받으면 이 설계와 겹친다
- 관심사 · 잘하는 것 · 가치관은 AI 가 첫 사건과 추천 방향을 정하는 데 쓸 수 있다

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| 성장과정 · 습관 · 버킷리스트 입력 | 긴 글 입력이라 시작이 늦어진다. 필요하면 게임 안 대화에서 자연스럽게 묻는다 |
| 건강 · 질병 입력 | 민감정보 |

### 한계와 보완
- 선택 항목이 AI 응답에 실제로 도움이 되는지는 플레이 테스트로 확인한다
- **변경 (2026-10-31):** 선택 항목은 시작 때 랜덤 2개만 보여 주고(건너뛰기 가능), 나머지는 게임 중 NPC 가 대화로 하나씩 묻는다. 건강 · 질병은 받지 않을 뿐 아니라 AI 가 묻거나 유도하지도 않는다

## 8. 3D 빌드 파일 위치 (2026-10-31)

### 결정
- 빌드 파일은 백엔드 서버 폴더(`/srv/builds/<buildId>/`)에 두고, Django 앞의 Nginx 가 `/builds/` 주소로 내려준다
- 빌드 파일은 Git 저장소에 넣지 않고 배포 때 서버로 복사한다. 저장소에는 빌드 카탈로그 JSON 만 둔다

### 근거
- Django(Gunicorn)로 수십 MB 파일을 보내면 그동안 worker 가 묶여 채팅 요청이 밀린다
- GitHub 은 50MB 이상 파일에 경고, 100MB 이상은 차단하고, 빌드를 바꿀 때마다 저장소가 커진다

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| Django 가 직접 내려주기 | worker 가 묶인다 |
| 백엔드 저장소 안 빌드 폴더 | GitHub 용량 제한 · 저장소 비대화 |
| 네이버 클라우드 Object Storage | 가능하지만 설정이 더 많다. 사용자가 늘면 다시 검토 |

### 한계와 보완
- Unity WebGL 용 헤더 설정이 필요하며 압축 방식에 따라 다르다 ([06 5-1](06-deployment.md#5-1-백엔드-서버-처음-세팅)). 현재 테스트 빌드는 비압축이다
- 프론트가 https 이므로 백엔드 서버에 도메인 · SSL 인증서가 필요하다

## 9. 종료 응답 없는 체험 정산은 Unity 명세 v003 을 따름 (2026-10-31)

### 결정
- 같은 플레이어가 새 체험을 시작할 때 프론트가 정산 요청을 보내고, 백엔드가 lease(마지막 생존 신호 뒤 120초) 만료를 확인해 `interrupted` 등으로 정산한다
- 정산 결과는 Unity 이벤트가 아닌 별도 `experience.reconciled` 로 응답한다
- 이벤트 재전송은 전송 큐 규칙(저장 확인까지 2초마다)을 따른다

### 근거
- Unity 담당 명세(v003)와 프론트 연결 코드가 이 규칙으로 만들어져 있다. 우리 규칙이 다르면 이중 집계 · 다른 탭 체험을 잘못 끝내는 문제가 생긴다

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| 플레이 재개 시 바로 "중간에 그만둠" 처리 (이전 결정) | 다른 탭에서 살아 있는 체험을 끝낼 수 있고, 늦게 도착한 실제 종료를 반영하지 못한다 |
| 재전송 최대 3회 (이전 결정) | 네트워크가 길게 끊기면 이벤트를 잃는다 |

### 한계와 보완
- lease · 원자적 소유권 처리 등 구현량이 늘어난다. 구현 때 `docs/unity/contracts/reconciliation-v003/acceptance-cases.json` 16개 사례로 확인한다

## 10. 배포 · SSL · CORS 담당 (2026-10-31)

### 결정
- 웹 프론트는 Vercel (SSL 자동). 백엔드는 네이버 클라우드 서버에서 Nginx + Let's Encrypt 로 SSL 처리
- API CORS 는 Django(django-cors-headers)만 붙인다. 빌드 iframe 은 Nginx `frame-ancestors` 로 프론트 주소만 허용

### 근거
- 프론트가 https 라 백엔드 · 빌드도 https 가 아니면 브라우저가 막는다
- CORS 헤더를 Nginx 와 Django 가 함께 붙이면 중복 헤더로 브라우저가 거부한다
- Unity 연결 코드가 빌드를 iframe 으로 열기 때문에, 빌드 쪽은 CORS 가 아니라 frame-ancestors 가 필요하다

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| 프론트 Railway | 가능하지만 정적 프론트에는 Vercel 이 더 간단 |
| Nginx 에서 CORS 처리 | Django 와 중복 위험, 설정이 두 곳으로 나뉜다 |

### 한계와 보완
- 백엔드 도메인이 있어야 SSL 을 받을 수 있다
- **변경 (2026-10-31):** 제공받은 서버는 사설 IP(10.1.1.14)에 SSL VPN 으로만 접속되고 공인 IP · 도메인이 없으며 제공처 설정을 바꿀 수 없다. 그래서 Let's Encrypt 대신 **Cloudflare Tunnel**(서버가 바깥으로 연결, 주소 `*.trycloudflare.com`, SSL 자동)로 공개한다. 서버의 바깥 연결과 외부(LTE) 접속을 확인했다. 프론트는 Vercel 그대로 두고, 터널 주소가 바뀌면 Vercel 환경변수만 바꿔 재배포한다 ([06 0절](06-deployment.md#0-배포-환경-한눈에))
  - 버린 대안: 프론트까지 같은 서버에 올리기 (CORS 는 없어지지만 Vercel 결정을 유지), 시연 PC 만 VPN 연결 (외부 사용자가 접속할 수 없음)
  - 한계: 무료 임시 터널은 재실행 때 주소가 바뀌고 가동 보장이 없다. 규정 확인 필요 ([11 F6](11-open-issues.md#f-확인이-필요한-질문))

## 11. 3D 연동 API 를 Unity 어댑터에 맞춤 (2026-10-31)

### 결정
- 이벤트 API 는 Unity 이벤트를 **원본 그대로** 받는다 (`/plays/{playId}/experience-events`). 이전의 `{buildId, …, unityEvent}` 감싸기는 없앤다
- 3D 연동 API 4개(이벤트 · 정산 · 생존 신호 · 미수신 기록)는 응답을 `{code, data}` 로 감싸지 않는다
- 프론트는 어댑터를 `credentials: 'omit'` · `X-Player-Id` 헤더로 만든다
- 종료 응답 미수신 기록 API(1-10)를 추가한다

### 근거
- Unity 담당의 `frontend/backend.js` 는 이벤트를 그대로 보내고 응답 본문을 그대로 읽는다. 이벤트 안에 빌드 · 방 · 시나리오 ID 가 이미 있다
- 어댑터 기본값 `credentials: 'include'` 는 쿠키를 보내는데 우리는 쿠키를 쓰지 않아 CORS 에서 막힌다

### 버린 대안
| 대안 | 버린 이유 |
|------|-----------|
| 어댑터를 고쳐 우리 형식에 맞춤 | Unity 담당 원본을 고치면 다음 전달 때마다 다시 고쳐야 한다 |

### 한계와 보완
- 공통 응답 형식에 예외가 생긴다. 03 공통 규약에 예외를 명시했다

### 한계와 보완
- 벡터 DB · 임베딩 · 모델 크기는 AI 담당이 정한다 ([11 A4](11-open-issues.md#a-스펙-미확정-항목)). 직업백과 데이터 이용 조건 확인이 필요하다
