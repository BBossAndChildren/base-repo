# 10. 프롬프트 조립 · 콘텐츠 연동

> 관련 문서: [02-architecture.md](02-architecture.md) · [03-api.md 2부](03-api.md#2부-백엔드--ai-서버) · [docs/game/](../game/README.md) · [docs/unity/](../unity/README.md)
> **시나리오 작가와 백엔드 담당이 함께 보는 문서다.** 작가가 `docs/game/` 에 쓰는 마크다운을 백엔드가 어떻게 읽어 AI 서버에 보내는지, 두 역할이 맞춰야 할 약속을 한곳에 모은다.

## 2. 프롬프트 조립 순서

> 시나리오 · 가이드라인 문서는 **매 AI 요청마다 고정으로** 넣는다 (하네스 역할). 공통 지침 문서는 백엔드 서버 한곳에 두고 수정하지 않는다. 플레이어마다 달라지는 내용은 DB 의 플레이어 기록에만 쓴다.

| 순서 | 넣는 것 | 출처 | 범위 |
|:---:|---------|------|------|
| 1 | 가이드라인 (세이프가드) | `docs/game/` | 모든 유저 공통 |
| 2 | 시나리오 | `docs/game/` | 모든 유저 공통 |
| 3 | 플레이어 기록 ([5절](#5-플레이어-기록-항목)) | 백엔드 DB | 플레이어별 |
| 4 | 아직 모르는 선택 항목 목록 (AI 가 대화 중 하나씩 묻도록) | 백엔드 DB | 플레이어별 |
| 4-1 | 최근 대화 **20턴** | 백엔드 DB | 플레이어별 |
| 5 | 이번 사용자 입력 | 프론트 요청 | — |

## 3. AI 응답 처리

- AI 서버는 자유 글이 아니라 **정해진 JSON** 으로 응답한다 (형식: [03-api.md 2-1](03-api.md#2-1-대화-생성))
- 백엔드는 응답의 `stateChanges` 를 그대로 반영하지 않고, 가이드라인과 현재 상태에 맞는지 확인한 뒤 반영한다 (예: 말만으로 직업이 바뀌는 변경은 버린다) <!-- TODO: 확인 규칙 목록 -->
- 선택 항목 질문: AI 는 아직 모르는 선택 항목을 대화 흐름에 맞을 때 **한 번에 하나씩**만 묻는다. 답을 받으면 `stateChanges` 에 `profile.<필드>` 로 담고, 백엔드는 선택 항목 7개 중 하나인지 확인한 뒤 저장한다 <!-- TODO: 질문 빈도 (예: 몇 턴에 한 번) -->
- 건강 · 질병: AI 는 묻거나 말하도록 유도하지 않는다. 사용자가 먼저 말해도 플레이어 기록에 저장하지 않는다. 시나리오 작가 가이드라인에도 같은 규칙을 넣도록 요청한다
- 형식이 깨진 응답이 오면 **1회 다시 요청**하고, 그래도 실패하면 프론트에 "잠시 후 다시 시도" 안내 오류를 준다

## 4. 3D 체험 연동

> 흐름 원문: [00-idea.md 서비스 구조](../00-idea.md#서비스-구조-회의-결정)
> Unity 는 직업별 장면을 시나리오로 미리 구성하므로 **에셋을 따로 지정하지 않는다.** 방(`roomId`) · 시나리오(`scenarioId`) 만 고른다.

1. 3D 가 필요한 분기에 도달하면 백엔드가 빌드 카탈로그 JSON(4-1)을 정리해 AI 서버에 추천을 요청한다 ([03-api.md 2-2](03-api.md#2-2-3d-체험-추천))
2. AI 서버는 빌드 · 방 · 시나리오를 추천한다
3. 백엔드는 추천이 카탈로그에 있는지 확인하고, **빌드 주소**와 `buildId` · `roomId` · `scenarioId` · `scenarioVersion` 을 프론트에 보낸다 (빌드는 여러 파일 · 수십 MB 라 API 응답에 직접 담지 않는다. 배포 방식은 [06 5-1](06-deployment.md#5-1-백엔드-game-마크다운--3d-빌드--빌드-카탈로그-json-포함))
4. 맞는 빌드가 없거나 카탈로그에 없는 추천이면 3D 를 건너뛰고 텍스트로 계속한다 (4-4)
5. 프론트가 빌드 주소를 iframe 으로 열고 Unity 에 체험 시작을 호출한다 (Unity 담당 연결 코드 `integration/frontend/` 사용 — [docs/unity/README.md](../unity/README.md))
6. Unity 는 물건 상태가 바뀔 때마다 이벤트를 실시간으로 보내고, 프론트는 받을 때마다 즉시 백엔드로 보낸다 (4-3)
7. 체험이 끝나면(`experience.ended`) 백엔드가 결과를 플레이어 기록에 한 번 반영하고 다음 프롬프트에 넣는다
8. 종료 응답이 오지 않은 체험은 다음 체험을 새로 시작할 때 백엔드가 정산한다 (4-5)

### 4-1. 빌드 카탈로그 JSON 형식

> 백엔드가 갖고 있는 빌드 목록이며 **이 목록에 있는 체험만 AI 가 추천할 수 있다** (실행 허용 목록). `buildId` · `roomId` · `scenarioId` · `scenarioVersion` 네 값은 Unity 와 **대소문자까지 정확히** 같아야 한다. 지금 실행되는 10개 체험은 [docs/unity/README.md](../unity/README.md#지금-실행되는-체험-buildid-career-pilot-v007-버전-모두-v002) 에 있다. `tx/career-integration-registry-v001.json` 의 552개는 참고용 ID 목록이며 실행 허용 목록이 아니다.

```json
{
  "builds": [
    {
      "buildId": "career-pilot-v007",
      "buildUrl": "/builds/career-pilot-v007/",
      "rooms": [
        {
          "roomId": "PAN-002",
          "concept": "행사 기획 사무실",
          "scenarios": [
            {
              "scenarioId": "career-net-951-experience",
              "scenarioVersion": "v002",
              "jobs": ["행사기획자"],
              "description": "TODO: 체험 내용 요약 (AI 가 고를 근거)"
            }
          ]
        }
      ]
    }
  ]
}
```

| 필드 | 설명 |
|------|------|
| `buildId` | 빌드 고유 ID (버전 포함). 한 빌드에 여러 방이 들어 있다 |
| `buildUrl` | 프론트가 빌드를 불러올 주소 |
| `rooms[].roomId` | Unity 방 ID (`PAN-NNN`) |
| `rooms[].concept` | 환경 콘셉트 (AI 가 읽는 설명) |
| `rooms[].scenarios[]` | 이 방에서 할 수 있는 직업별 체험. `jobs` 와 `description` 은 AI 가 고를 근거 |

> 값의 출처: ID 는 Unity 담당 목록, `concept` · `description` 은 백엔드가 작성한다.

### 4-2. 체험 결과값 형식 (Unity → 프론트)

> **원본: [`docs/unity/`](../unity/README.md) — 송수신 명세 `tx/` (프로필 v003).** Unity 담당이 관리하며 이 문서에 다시 쓰지 않는다.
> 상태: Unity 실시간 송신 · 프론트 수신은 테스트 빌드(10개 체험)로 동작 확인. 실서비스 백엔드 저장 · 종료 미수신 정산은 미구현.

| 응답 | 의미 | 백엔드가 쓰는 곳 |
|------|------|------------------|
| 실시간 이벤트 (`object.selected` · `interaction.*` · `scenario.*` 등) | 상태가 확정될 때마다 Unity 가 실시간으로 보냄. 종류 · 필수 필드는 `tx/realtime-contract.json` | 이벤트 누적 · 최신 상태 |
| `experience.started` | 방·시나리오 준비 완료 | 체험 시작 기록 |
| `experience.ended` | 체험 종료. `result.outcome` 이 `completed` · `aborted` · `failed` 중 하나 | 플레이어 기록 반영 (과정 `process` · 결과 `result` · 해석 `context`) |
| `experience.error` | 호출·라우팅 오류. 업무 실수가 아님 | 체험 종료 → 텍스트 모드 전환 |

백엔드가 결과를 해석할 때 지킬 것 (명세 원문 기준):
- 카운트가 `null` 이면 미측정이다. 0회로 해석하지 않는다
- 평가 코드(`TASK_SMOOTH` 등)는 이번 가상 업무의 수행 설명이며 개인의 적성·능력 점수가 아니다. AI 프롬프트에도 그렇게 전달한다
- 중도 종료(`aborted`)여도 이미 완료한 결과는 `result.data.partialResults` 에 남는다
- 탭 강제 종료 · 통신 단절은 마지막 응답이 보장되지 않으므로 사용자 포기로 단정하지 않는다
- `process` 의 횟수는 **누적값**이다. 이벤트끼리 더하지 않고, 범위(`scenarioRunId` · scope · stepId 등)별 **가장 큰 `sequence`** 의 값을 최신 상태로 쓴다
- 초기화(`scenario.reset`)로 나뉜 이전 실행은 `previousRuns` 로 따로 두며 현재 실행에 더하지 않는다

### 4-3. 프론트 → 백엔드 전달

- 프론트는 Unity 응답을 **받을 때마다 즉시** 백엔드로 보낸다 ([03-api.md 1-4](03-api.md#1-4-3d-체험-이벤트-전달)). 덧붙이는 값: `buildId` · `roomId` · `scenarioId` · `scenarioVersion`
- 묶음 ID 는 Unity 명세의 `sessionId`(플레이 동안 유지) · `experienceId`(체험 시작마다 프론트가 새로 생성)를 그대로 쓴다
- **전송 큐:** 프론트는 Unity 연결 코드의 전송 큐(`createOutbox`)를 쓴다. 이벤트를 브라우저 저장소에 보관하고, 백엔드의 **저장 확인(ACK)** 을 받을 때까지 2초마다 같은 이벤트를 다시 보낸다 (횟수 제한 없음)
- **저장 확인:** 백엔드는 DB 저장을 마친 뒤에만 `{stored: true, sessionId, eventId}` 를 돌려준다. 단순 접수 응답을 저장 확인으로 쓰지 않는다
- **중복 · 충돌:** 백엔드는 `(sessionId, eventId)` 로 중복을 제거한다. 같은 ID 에 내용이 다르면 충돌로 거부한다
- **순서:** 늦게 도착한 이벤트도 저장하되, 더 최신 상태를 덮어쓰지 않는다
- 백엔드는 이벤트를 쌓다가 `experience.ended` 를 받으면 한 번 플레이어 기록에 반영한다

### 4-5. 종료 응답이 오지 않은 체험 정산 (v003)

> 원본: `docs/unity/tx/README.md` · `interruption-contract.json`. **구현 담당: 백엔드.**

| 단계 | 내용 |
|------|------|
| 종료 대기 | 프론트는 종료 호출 후 5초 기다린다. 5초가 지나도 중단 확정이 아니며 같은 `requestId` 로 다시 보낸다 |
| 체험 중 생존 신호 | 프론트는 체험 중 30초마다 생존 신호(heartbeat)를 보낸다. 백엔드는 마지막 신호 뒤 120초가 지나면 그 체험의 소유(lease)를 만료로 본다 |
| 정산 시점 | **같은 플레이어가 새 체험을 시작할 때** 프론트가 정산 요청(reconcile)을 보낸다 ([03 1-8](03-api.md#1-8-종료-응답-없는-체험-정산)). 재접속만 한 경우는 기존 체험을 유지한다 |
| 판정 | 다른 탭에서 살아 있으면 `deferred_active`, 확인 불가면 `pending_reconciliation`, 새 시작 + lease 만료면 `interrupted`, 시작 근거가 없으면 `not_started` |
| 화면 문구 | 종료 응답을 받지 못해 이전 체험을 중단 처리했습니다. |
| 금지 | 사용자 포기 · 실수로 해석하지 않는다. 실수 · 재시도 횟수를 더하지 않는다. 서버 정산을 Unity `experience.ended` 로 꾸미지 않는다 (`experience.reconciled` 로 따로 응답) |
| 늦게 도착한 실제 종료 | 검증 후 같은 `resolutionId` 의 다음 revision 으로 정정한다. 이전 기록은 남긴다 |

구현 때 확인할 사례 16개: `docs/unity/tx/acceptance-cases.json`

### 4-4. 오류 안내 문구

| 상황 | 방식 | 문구 |
|------|------|------|
| 맞는 빌드가 없음 · 추천이 카탈로그에 없음 | 토스트 | 지금 상황에 맞는 3D 체험이 없어 텍스트로 이야기를 이어갈게요. |
| 빌드 로딩 실패 | 토스트 | 3D 체험을 불러오지 못했어요. 이번 체험은 건너뛰고 텍스트로 이어갈게요. |
| 체험 중 `experience.error` · 명세에 맞지 않는 값 · 내부 오류 | 모달 + [텍스트로 계속하기] | 체험 중 문제가 생겨 3D 체험을 종료했어요. 지금까지 한 체험은 저장되었어요. 텍스트 모드로 이어서 진행해 주세요. |
| 이전 체험 정산 결과 `interrupted` | 토스트 | 종료 응답을 받지 못해 이전 체험을 중단 처리했습니다. |
