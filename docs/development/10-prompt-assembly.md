# 10. 프롬프트 조립 · 콘텐츠 연동

> 관련 문서: [02-architecture.md](02-architecture.md) · [03-api.md 2부](03-api.md#2부-백엔드--ai-서버) · [docs/game/](../game/README.md) · [docs/unity/](../unity/USAGE.md)
> **시나리오 작가와 백엔드 담당이 함께 보는 문서다.** 작가가 `docs/game/` 에 쓰는 마크다운을 백엔드가 어떻게 읽어 AI 서버에 보내는지, 두 역할이 맞춰야 할 약속을 한곳에 모은다.
> 게임 콘텐츠 자체(시나리오·NPC·가이드라인 내용)는 `docs/game/` 에만 쓴다. 이 문서에는 **읽는 규칙과 조립 순서**만 쓴다.

## 2. 프롬프트 조립 순서

> 시나리오 · 가이드라인 문서는 **매 AI 요청마다 고정으로** 넣는다 (하네스 역할). 공통 지침 문서는 백엔드 서버 한곳에 두고 수정하지 않는다. 플레이어마다 달라지는 내용은 DB 의 플레이어 기록에만 쓴다.

| 순서 | 넣는 것 | 출처 | 범위 |
|:---:|---------|------|------|
| 1 | 가이드라인 (세이프가드) | `docs/game/00-guidelines.md` | 모든 유저 공통 |
| 2 | 세계관 · 시나리오 · 규칙 · NPC | `docs/game/01` · `02` · `03` · `05` · `06` (충돌 시 최신 상세 기획 우선) | 모든 유저 공통 |
| 3 | 플레이어 기록 ([5절](#5-플레이어-기록-항목)) | 백엔드 DB | 플레이어별 |
| 4 | 아직 모르는 선택 항목 목록 (AI 가 대화 중 하나씩 묻도록) | 백엔드 DB | 플레이어별 |
| 4-1 | 최근 대화 **20턴** 중 현재 발화 NPC가 알 수 있는 내용 | 백엔드 DB | 플레이·NPC별 |
| 5 | 이번 사용자 입력 | 프론트 요청 | — |

> **직업 정보는 백엔드가 넣지 않는다.** AI 서버(Qwen)가 RAG 로 직업 데이터(직업백과 552개)에서 대화에 관련된 직업을 찾아 스스로 붙인다 ([6절](#6-직업-데이터-rag-ai-서버)).

## 3. AI 응답 처리

- AI 서버는 자유 글이 아니라 **정해진 JSON** 으로 응답한다 (형식: [03-api.md 2-1](03-api.md#2-1-대화-생성))
- 백엔드는 응답의 `stateChanges` 를 그대로 반영하지 않고, 가이드라인과 현재 상태에 맞는지 확인한 뒤 반영한다 (예: 말만으로 직업이 바뀌는 변경은 버린다) <!-- TODO: 확인 규칙 목록 -->
- 선택 항목 질문: AI 는 아직 모르는 선택 항목을 대화 흐름에 맞을 때 **한 번에 하나씩**만 묻는다. 답을 받으면 `stateChanges` 에 `profile.<필드>` 로 담고, 백엔드는 선택 항목 7개 중 하나인지 확인한 뒤 저장한다 <!-- TODO: 질문 빈도 (예: 몇 턴에 한 번) -->
- 건강 · 질병: AI 는 묻거나 말하도록 유도하지 않는다. 사용자가 먼저 말해도 플레이어 기록에 저장하지 않는다. 시나리오 작가 가이드라인에도 같은 규칙을 넣도록 요청한다
- 형식 또는 상태 규칙 검증에 실패하면 **1회 다시 요청**하고, 그래도 실패하면 프론트에 "잠시 후 다시 시도" 안내 오류를 준다. 실패한 턴의 상태와 성공 대화를 부분 저장하지 않는다. 같은 요청 ID 재전송은 같은 확정 결과를 반환한다

## 4. 3D 체험 연동

> 흐름 원문: [00-idea.md 서비스 구조](../00-idea.md#서비스-구조-회의-결정)
> Unity 는 직업별 장면을 시나리오로 미리 구성하므로 **에셋을 따로 지정하지 않는다.** 방(`roomId`) · 시나리오(`scenarioId`) 만 고른다.

1. AI 대화 응답에 **분기 주제 `branch`** 가 오면(AI 가 "지금이 3D 체험 분기"라고 판단) 백엔드가 이를 감지하고 빌드 카탈로그 JSON(4-1)을 정리해 AI 서버에 추천을 요청한다 ([03-api.md 2-2](03-api.md#2-2-3d-체험-추천))
2. AI 서버는 빌드 · 방 · 시나리오를 추천한다
3. 백엔드는 추천이 카탈로그에 있는지 확인하고, **빌드 주소**와 `buildId` · `roomId` · `scenarioId` · `scenarioVersion` + 화면 표시용 `title` · `jobs` · `reason` 을 프론트에 보낸다 (빌드는 여러 파일 · 수십 MB 라 API 응답에 직접 담지 않는다. 배포 방식은 [06 5-2](06-deployment.md#5-2-3d-빌드-파일-저장--관리--전달))
4. 맞는 빌드가 없거나 카탈로그에 없는 추천이면 3D 를 건너뛰고 텍스트로 계속한다 (4-4)
5. 프론트가 빌드 주소를 iframe 으로 열고 Unity 에 체험 시작을 호출한다 (Unity 담당 연결 코드 `docs/unity/frontend/` 사용 — [docs/unity/USAGE.md](../unity/USAGE.md))
6. Unity 는 물건 상태가 바뀔 때마다 이벤트를 실시간으로 보내고, 프론트는 받을 때마다 즉시 백엔드로 보낸다 (4-3)
7. 체험이 끝나면(`experience.ended`) 백엔드가 결과를 플레이어 기록에 한 번 반영하고 다음 프롬프트에 넣는다
8. 종료 응답이 오지 않은 체험은 다음 체험을 새로 시작할 때 백엔드가 정산한다 (4-5)

### 4-1. 빌드 카탈로그 (Unity 제공)

> **Unity 담당이 준 카탈로그를 그대로 쓴다:** `docs/unity/builds/production-ai-build-catalog.json` (실서비스 빌드 `career-suite-integration-v005`). 테스트 빌드는 `test-ai-build-catalog.json`. 우리가 따로 만들지 않는다.
> 허용 목록은 같은 폴더의 `production-supported-manifest.json` 이다. 추천 결과의 `buildId` + `roomId` + `scenarioId` + `scenarioVersion` 네 값이 이 목록과 **대소문자까지 정확히** 맞아야 한다. 이전 빌드 목록으로는 대조하지 않는다.

`experiences[]` 한 줄 (555개, 71개 방 · 552개 시나리오):
```json
{
  "buildId": "career-suite-integration-v005",
  "roomId": "PAN-002",
  "scenarioId": "career-net-951-experience",
  "scenarioVersion": "v002",
  "jobs": ["행사기획자"],
  "description": "「행사 요청서」의 행사명·날짜·인원 항목을 직접 입력·저장하고, …",
  "runtimeFamily": "career-pilot-direct-work",
  "verificationStatus": "unverified_this_build"
}
```

| 규칙 | 내용 |
|------|------|
| 추천 범위 | **555개 전부 허용**한다. 모두 "이번 빌드 미검증"이므로 체험 중 오류가 나면 4-4 처럼 텍스트로 넘어간다. 시연은 끝까지 확인한 체험 위주로 한다 |
| 후보 줄이기 | 설명만 약 8만 7천 자라 매번 전부 보낼 수 없다. **백엔드가 먼저 후보 20개로 줄여** AI 서버에 보낸다 (4-1-1) |
| 빌드 경로 | 빌드 파일은 `/srv/builds/<buildId>/` 에 두고, 백엔드는 현재 요청 주소를 붙여 `buildUrl` 로 준다 ([06 5-2](06-deployment.md#5-2-3d-빌드-파일-저장--관리--전달)) |
| `description` 의 의미 | 체험 내용 설명이다. 사용자의 적성 · 자격 · 능력 판정 자료로 쓰지 않는다 |

#### 4-1-1. 후보 20개 고르는 방식 (BE7)

> 1단계는 **점수 + 탐색 섞기** 로 시작한다. 플레이 테스트에서 엉뚱한 후보가 많으면 2단계(AI 서버 임베딩 유사도)로 바꾼다 ([12 결정 18](12-decisions.md)).

1. **제외:** 이 플레이에서 이미 체험한 시나리오
2. **점수 계산** (카탈로그 555개 각각)

| 조건 | 점수 |
|------|:---:|
| 희망 직업(`dreamJob`)이 `jobs` 의 직업명과 겹침 (부분 일치) | +10 |
| 최근 20턴 대화에 `jobs` 의 직업명이 나옴 (사용자 · NPC 모두) | +5 |
| 관심사 · 잘하는 것의 단어가 `description` 에 들어 있음 | 단어마다 +2 (최대 +6) |
| AI 응답 `branch.jobs` 가 `jobs` 와 겹침 | +8 |
| AI 응답 `branch.topic` 의 단어가 `jobs` · `description` 에 들어 있음 | +5 |

3. **점수 높은 순 최대 12개** (0점은 넣지 않음)
4. **나머지를 무작위로 채워 20개:** 아직 고르지 않은 **서로 다른 방(roomId)** 에서 하나씩. 희망 직업이 없는 사용자도 새로운 일을 만나게 하려는 것이다 (00-idea 4장 "희망 직업이 없는 경우")
5. 후보 20개의 `buildId` · `roomId` · `scenarioId` · `scenarioVersion` · `jobs` · `description` 만 AI 서버에 보낸다 ([03 2-2](03-api.md#2-2-3d-체험-추천))

- 단어 일치는 공백 · 가운뎃점(ㆍ · ·) · 괄호를 지우고 비교한다 (예: "제빵사" ↔ "제과사 및 제빵사")
- 같은 입력이면 점수 부분은 같은 결과가 나와야 한다 (테스트 V13)

### 4-2. 체험 결과값 형식 (Unity → 프론트)

> **원본: [`docs/unity/`](../unity/USAGE.md) — 송수신 명세 `contracts/` (실시간 v002 · 정산 v003).** Unity 담당이 관리하며 이 문서에 다시 쓰지 않는다.
> 상태: Unity 실시간 송신 · 프론트 수신은 테스트 빌드(10개 체험)로 동작 확인. 실서비스 백엔드 저장 · 종료 미수신 정산은 미구현.

| 응답 | 의미 | 백엔드가 쓰는 곳 |
|------|------|------------------|
| 실시간 이벤트 (`object.selected` · `interaction.*` · `scenario.*` 등) | 상태가 확정될 때마다 Unity 가 실시간으로 보냄. 종류 · 필수 필드는 `docs/unity/contracts/realtime-v002/realtime-contract.json` | 이벤트 누적 · 최신 상태 |
| `experience.started` | 방·시나리오 준비 완료 | 체험 시작 기록 |
| `experience.ended` | 체험 종료. `result.outcome` 이 `completed` · `aborted` · `failed` 중 하나 | 플레이어 기록 반영 (과정 `process` · 결과 `result` · 해석 `context`) |
| `experience.error` | 호출·라우팅 오류. 업무 실수가 아님 | 체험 종료 → 텍스트 모드 전환 |

백엔드가 결과를 해석할 때 지킬 것 (명세 원문 기준):
- 카운트가 `null` 이면 미측정이다. 0회로 해석하지 않는다
- 평가 코드(`TASK_SMOOTH` 등)는 이번 가상 업무의 수행 설명이며 개인의 적성·능력 점수가 아니다. AI 프롬프트에도 그렇게 전달한다
- 중도 종료(`aborted`)여도 이미 완료한 결과는 `result.data.partialResults` 에 남는다
- 탭 강제 종료 · 통신 단절은 마지막 응답이 보장되지 않으므로 사용자 포기로 단정하지 않는다
- `process` 의 횟수는 **누적값**이다. 이벤트끼리 더하지 않고, 범위(`scenarioRunId` · scope · stepId 등)별 **가장 큰 `sequence`** 의 값을 최신 상태로 쓴다
- 초기화(`scenario.reset`)로 나뉜 이전 실행은 `previousRuns` 로 따로 두며 현재 실행에 더하지 않는다

### 4-3. 프론트 → 백엔드 전달

- 프론트는 Unity 응답을 **받을 때마다 즉시** 백엔드로 보낸다 ([03-api.md 1-4](03-api.md#1-4-3d-체험-이벤트-전달)). 덧붙이는 값: `buildId` · `roomId` · `scenarioId` · `scenarioVersion`
- 묶음 ID 는 Unity 명세의 `sessionId`(플레이 동안 유지) · `experienceId`(체험 시작마다 프론트가 새로 생성)를 그대로 쓴다
- **전송 큐:** 프론트는 Unity 연결 코드의 전송 큐(`createOutbox`)를 쓴다. 이벤트를 브라우저 저장소에 보관하고, 백엔드의 **저장 확인(ACK)** 을 받을 때까지 2초마다 같은 이벤트를 다시 보낸다 (횟수 제한 없음)
- **저장 확인:** 백엔드는 DB 저장을 마친 뒤에만 `{stored: true, sessionId, eventId}` 를 돌려준다. 단순 접수 응답을 저장 확인으로 쓰지 않는다
- **중복 · 충돌:** 백엔드는 `(sessionId, eventId)` 로 중복을 제거한다. 같은 ID 에 내용이 다르면 충돌로 거부한다
- **순서:** 늦게 도착한 이벤트도 저장하되, 더 최신 상태를 덮어쓰지 않는다
- 백엔드는 이벤트를 쌓다가 `experience.ended` 를 받으면 한 번 플레이어 기록에 반영한다

### 4-5. 종료 응답이 오지 않은 체험 정산 (v003)

> 원본: `docs/unity/contracts/CONTRACT-SNAPSHOT.md` · `contracts/reconciliation-v003/interruption-contract.json`. **구현 담당: 백엔드.**

| 단계 | 내용 |
|------|------|
| 종료 대기 | 프론트는 종료 호출 후 5초 기다린다. 5초가 지나도 중단 확정이 아니며 같은 `requestId` 로 다시 보낸다 |
| 체험 중 생존 신호 | 프론트는 체험 중 30초마다 생존 신호(heartbeat)를 보낸다. 백엔드는 마지막 신호 뒤 120초가 지나면 그 체험의 소유(lease)를 만료로 본다 |
| 정산 시점 | **같은 플레이어가 새 체험을 시작할 때** 프론트가 정산 요청(reconcile)을 보낸다 ([03 1-8](03-api.md#1-8-종료-응답-없는-체험-정산)). 재접속만 한 경우는 기존 체험을 유지한다 |
| 판정 | 다른 탭에서 살아 있으면 `deferred_active`, 확인 불가면 `pending_reconciliation`, 새 시작 + lease 만료면 `interrupted`, 시작 근거가 없으면 `not_started` |
| 화면 문구 | 종료 응답을 받지 못해 이전 체험을 중단 처리했습니다. |
| 금지 | 사용자 포기 · 실수로 해석하지 않는다. 실수 · 재시도 횟수를 더하지 않는다. 서버 정산을 Unity `experience.ended` 로 꾸미지 않는다 (`experience.reconciled` 로 따로 응답) |
| 늦게 도착한 실제 종료 | 검증 후 같은 `resolutionId` 의 다음 revision 으로 정정한다. 이전 기록은 남긴다 |

구현 때 확인할 사례 16개: `docs/unity/contracts/reconciliation-v003/acceptance-cases.json`

## 7. 결말 · 추천 직업 (BE12 · AI5)

> 인생이 끝나면(AI 응답 `lifeEnded: true`) 결말과 추천 직업 3개를 만든다. **1차안 — 플레이 테스트 후 조정한다.**

**1단계 — 백엔드가 근거를 모으고 직업 점수를 매긴다**

| 근거 | 점수 (직업마다) |
|------|:---:|
| 3D 체험을 **완료**한 직업 (`outcome: completed`) | +5 |
| 3D 체험을 중간에 그만둔 직업 (`aborted`) | +2 |
| 흥미 기록(`state` 의 흥미)과 관련된 직업 | +3 |
| 대화에서 사용자가 관심을 보이며 언급한 직업 | +2 |
| 희망 직업 | +2 (희망 직업이 있으면 항상 후보에 넣는다) |

- 점수 상위 **5개** 직업과 근거(어떤 체험 · 대화에서 나왔는지)를 AI 서버에 보낸다
- 3D 평가 코드(`TASK_SMOOTH` 등)는 점수에 쓰지 않는다. 적성 · 능력 판정이 아니기 때문이다
- 근거가 거의 없으면(짧게 끝난 플레이) 희망 직업과 대화 속 직업만으로 만든다

**2단계 — AI 서버가 결말 문장과 추천 3개를 만든다** ([03 2-3](03-api.md#2-3-결말-생성))
- 결말: 이번 인생 요약 (어떤 선택 · 경험을 했는지)
- 추천 3개: 직업마다 **추천 이유**(이번 플레이의 근거) + **하는 일** + **다음 준비 방향 2~3개** — 직업 정보 · 준비 방법은 RAG 의 직업백과 근거
- 하나는 **아직 경험하지 않은 새 직업**을 넣어 다음 플레이를 권한다 (반복 플레이)

**표현 원칙**
- "당신에게 맞는 직업"이 아니라 "이번 인생에서 관심을 보인 일" · "다음에 경험해 볼 일"로 표현한다
- 진로 · 취업 보장, 적성 판정으로 말하지 않는다 (07 L6 AI09)

## 8. 최신 기획의 생성·기억 원칙

- 모르는 직업은 NPC가 성격에 맞게 모른다고 말하고 근거가 있는 관련 직업을 제안한다. 관심이나 한 번의 행동으로 적성을 확정하지 않는다.
- 핵심 업무는 그 직업을 이해하는 데 필요한 장면을 골라 자세히 경험하게 한다. 자유 입력은 문구 일치가 아니라 의도·업무 목적을 기준으로 후하게 판단하며 힌트와 재시도 기회를 제공한다.
- 반복 일상을 압축하면 경과 요약을 주고, 큰 기간은 확인받으며 선택이 필요한 사건에서 멈춘다. 월별 재정·상태 계산의 확정 주체는 백엔드다.
- 기억 검색은 백엔드가 허용한 플레이·NPC 범위를 AI 서버에 전달한 뒤 수행한다. 전체 대화나 전체 NPC 기억을 무조건 붙이지 않는다.
- 배경 정보 전달은 시간 경과·중요 사건에서만 제안한다. 전달 사실과 듣는 인물의 감정·해석을 분리하고, 백엔드가 검증한 뒤 기억에 추가한다.
- 실제 직업 사실에는 출처와 확인 시점을 유지한다. 개별 사업장의 채용 조건을 모든 직장의 공통 조건으로 만들지 않는다. 생성한 업무 상황은 실제 일어난 사건이라고 주장하지 않는다.
- 공통 지침은 매 요청 유지하고, 장기 기억은 관련 요약만 검색한다. 새 NPC와 대화할 때도 현재 플레이 상태는 이어지지만 그 NPC가 모르는 사실을 대사로 노출하지 않는다.
